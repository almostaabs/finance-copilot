# T1.3: Eval-driven coverage + public scoreboard

## Goal

Raise coverage (fewer withheld values) **without increasing wrong values**, by growing the alias and
blocked-label tables from real dev-set failures. Then publish the results as a generated scoreboard,
`docs/EVAL_RESULTS.md`, linked from the README.

## Why

The current coverage on real reports ranges from 5/19 to 14/19 concepts. Most gaps are labels no alias
table knows. Widening the tables from real failures is the fix `docs/KNOWN_ISSUES.md` #0b already names
("widening the alias tables from more real reports is the only safe fix; fuzzy matching stays out"). The
dev/holdout split is what stops this turning into overfitting.

## Prerequisites

T1.2 merged (both truth sources exist, both dev baselines committed).

## Read first

- `src/fincopilot/mapping/synonyms.py` in full: `normalize_label`, `CANONICAL`, `INDIAN_ALIASES`,
  `US_ALIASES`, `BLOCKED`, `match_label`, `map_rows`, and the section-header / bare "Total" logic
- `src/fincopilot/mapping/validate.py` (how conflicts arise when two rows claim a concept)
- `tests/test_mapping_synonyms.py`, `tests/test_mapping_golden.py`
- `pipeline.py` (the public stage functions you will call from the diagnose tool)
- `evals/results/baseline_dev.json`, `evals/results/baseline_manual_dev.json`

## Scope

In: `evals/diagnose.py`, `evals/report.py`, alias/blocked-list additions, their tests,
`docs/EVAL_RESULTS.md`, README accuracy section.
Out: fuzzy matching of any kind, changes to extraction/locating logic (log those as KNOWN_ISSUES
for a future phase), and looking at holdout failures.

## Hard rules for this phase

1. **Never look at holdout records.** `diagnose.py` refuses `--split holdout`.
2. **Every alias added must be a literal, normalised label** (run it through `normalize_label` and store the
   output). No regex, no prefix matching, no "contains".
3. **An alias is added only if all three hold:**
   - it fixes at least one dev `withheld` record (the diagnose tool shows the truth value sitting on a row
     with this label);
   - adding it creates **zero** new `wrong` records across *all* dev filings (checked by re-running the eval);
   - it is a label that means the concept in general financial reporting, not a company-specific quirk. If in
     doubt, write it to the "rejected candidates" list in the log with the reason, and do not add it.
4. **A new `BLOCKED` entry** is added when a label maps to a concept but its value is `wrong` (e.g. a
   subtotal that looks like the total). The same zero-new-wrong rule applies.
5. **Each alias or blocked entry gets a test** in `tests/test_mapping_synonyms.py`: one parametrised test row
   per label asserting `match_label(label, kind)` returns the concept (or `None` for blocked).
6. Work in **batches of at most 10 table entries**. After each batch: full gate + dev eval with `--compare`.
   If `wrong` increased, revert the whole batch, then re-add entries one at a time to find the culprit.

## Step 1: build `evals/diagnose.py`

```
uv run python -m evals.diagnose --split dev [--only TICKER_OR_ID ...] [--concept revenue ...]
```

For every `withheld` and `wrong` record in `evals/results/latest_dev.json` (and the manual equivalent):

1. Re-run the stages up to normalisation for that filing by calling the **public stage functions** directly,
   exactly as `pipeline.analyze` does: `validate_input` → `extract_pdf` → `locate_statements` →
   `detect_periods` → `normalize_document`. Do **not** modify `pipeline.py` to expose them.
2. Search every `NormalizedCell` in the statement the concept belongs to (`CONCEPT_STATEMENT[concept]`)
   for a value equal to the truth within the T1.1 tolerance (same sign rules).
3. Classify the record into exactly one category:

| category | meaning | typical fix |
|---|---|---|
| `STATEMENT_NOT_LOCATED` | the statement itself is `Unavailable` | out of scope → KNOWN_ISSUES |
| `PERIOD_FAILURE` | periods `Unavailable` or year not in the period map | out of scope → KNOWN_ISSUES |
| `LABEL_UNKNOWN` | truth value found on a row whose label maps to nothing | **candidate alias** |
| `LABEL_BLANK` | truth value found on a row with an empty label | out of scope (KNOWN_ISSUES #0b) |
| `CONFLICT` | two rows claim the concept | candidate BLOCKED entry for the wrong one |
| `WRONG_ROW` | mapped row's value ≠ truth, and truth sits on another row | candidate BLOCKED entry |
| `NOT_IN_STATEMENT` | truth value not found anywhere in the statement | check scale/sign; else truth may be on a note page → skip |
| `SCALE_OR_SIGN` | truth found only after a ×1000 / ×10⁵ / ×10⁷ / sign change | extraction bug → KNOWN_ISSUES, **stop and ask** if frequent |

4. Output `evals/results/diagnose_dev.md`: counts per category, then per category the records with filing,
   concept, year, candidate row label (raw and normalised), page and ref_id. For `LABEL_UNKNOWN`, group by
   normalised label and count distinct filings. **Labels seen in ≥2 filings come first**, since they are the
   strongest candidates.

Test `diagnose`'s classifier with small hand-built inputs (`tests/test_evals_diagnose.py`), one test per
category.

## Step 2: coverage loop

Repeat until no `LABEL_UNKNOWN` candidate seen in ≥2 filings remains, or three batches in a row
produce no improvement:

1. Run the eval (dev), then `diagnose`.
2. Pick up to 10 candidates, most filings first. Apply hard rules 2–4 to each.
3. Add them to the right table (`US_ALIASES` for US filings, `INDIAN_ALIASES` for Indian ones; if a label
   appears in both, add it to both and say so in the commit message). Add tests (rule 5).
4. Gate + `--compare` against the current baseline. Pass → save the new baseline in its own commit
   (`eval: coverage batch N, +x correct, wrong unchanged`). Fail → revert the batch, then bisect.
5. Log the batch: entries added, records fixed, rejected candidates with reasons.

Single-filing labels are added **only** after the ≥2-filing ones are exhausted, and only if clearly general
(e.g. a standard US GAAP caption with slightly different wording).

## Step 3: scoreboard generator `evals/report.py`

```
uv run python -m evals.report --out docs/EVAL_RESULTS.md
```

Generates (never hand-edit the output):

- Header: run date, git SHA, how to reproduce, link to `evals/README.md`.
- Definitions (copy from the tier README), and the note on rendered EDGAR PDFs vs company PDFs.
- Totals table, one row per (source × bucket × split): filings, correct, wrong, withheld, precision,
  coverage, wrong rate, errors. Holdout rows show "not yet run" until the tier exit gate.
- Per-concept table (dev).
- **Every `wrong` record** listed in full. Hiding them would undercut the whole point.
- Known limitations: concepts not scored, financial bucket caveat, number of unverified Indian files.

Add a test that runs `report` over a small fixture results JSON and checks that all sections are present.

## Step 4: README

Add an **Accuracy** section near the top of the README with a 3-row summary table (US general dev, US
financial dev, India dev) plus a link to `docs/EVAL_RESULTS.md`, and one sentence explaining "wrong" vs
"withheld". Numbers are copied from the generated file, never rounded more favourably. The headline wording
is fixed: "**Wrong values: N of M checked**", not an accuracy percentage on its own.

## Acceptance criteria

1. `diagnose.py` exists, refuses holdout, and is tested per category.
2. At least one coverage batch was completed through the full loop, with the log entry.
3. `wrong` on dev (both sources) is **≤ the T1.2 baselines**; coverage is ≥ baseline. Report both deltas.
4. Every added alias/blocked entry has a test and appears in the log with the filings it fixed.
5. `docs/EVAL_RESULTS.md` is generated, committed, and lists every wrong record.
6. The README accuracy section matches the generated file exactly.
7. No fuzzy/regex/contains matching was added: `git diff main -- src/fincopilot/mapping/` shows only
   string literals and tests.

## Phase-specific checks

- Evaluator: for 5 random new aliases, confirm from the diagnose output that the label appeared in the
  claimed filings, and that no dev record went from correct/withheld to wrong.
- Evaluator: confirm no holdout file was read. `grep -rn holdout evals/results/diagnose_dev.md` must be empty.

## Stop and ask if

- `SCALE_OR_SIGN` is more than 5% of failures (that is an extraction bug and outside this phase's scope).
- Adding a clearly correct, general alias creates a `wrong` (that means a deeper mapping or conflict issue).

## Subagent split

Builder: steps 1 and 3 (tools). Then per batch: a builder proposes and adds entries, and a fresh evaluator runs
the gate + compare and checks rule 3 for each entry. The orchestrator commits the baseline only on the
evaluator's PASS.
