# T3.3: Next.js frontend (optional)

## Decision step: should this be done at all? (answer first; record it in the log)

Do this phase only if at least one is true:

- The Streamlit UI is demonstrably limiting a feature someone asked for (list the feature).
- A target role specifically values frontend or full-stack work, and the portfolio lacks it.
- The hosted Streamlit demo's cold start or layout is losing reviewers (with evidence, e.g. feedback).

If none holds, **skip this phase**, mark it "skipped: <reason>" in the status table, and stop. A rewrite that
changes nothing a reviewer checks costs weeks and adds a second deployment to maintain. This is a legitimate
outcome, not a failure.

## Goal (if done)

A Next.js frontend over a small Python API, with feature parity for: upload, sample report, results
dashboard, provenance + source viewer, multi-year, compare, Q&A. The Python analysis code is unchanged.
Streamlit stays deployed until parity is verified.

## Design (fixed if the phase goes ahead)

1. **API**: `api/` package using FastAPI (a new optional dependency group `api`). Endpoints:
   - `POST /analyze` (multipart PDF, ≤ the existing `DEFAULT_MAX_BYTES`) → `{analysis_id, result}`
   - `GET /analysis/{id}/source?value=<concept@year>` → PNG from `source_view.render_cell`
   - `POST /analysis/{id}/ask` → Q&A (only when a provider is configured server-side)
   - `GET /edgar/filings?ticker=` and `POST /analyze/edgar` (if the T2.2 hosted spike said rendering works)
2. **Serialisation**: one module, `api/serialize.py`, turns `AnalysisResult` into JSON. **Decimals become
   strings** and are never converted to floats. `Unavailable` becomes `{"unavailable": {reason, detail, root}}`.
   The frontend does all formatting through a single `formatNumber` that mirrors `display.py`'s rounding
   rules; a test pins the two against each other on the golden fixtures.
3. **State**: in-memory LRU of analyses (max 20, 30-minute TTL), with no disk persistence, matching the hosted
   demo's privacy rule that no visitor sees another's data. Analysis IDs are random 128-bit.
4. **Security**: size and page limits enforced before parsing (reuse `validate_input`), CORS locked to the
   frontend origin, no user-supplied names in paths, rate limit per IP on `/analyze` and `/ask`, and escaping
   handled by React (no `dangerouslySetInnerHTML` anywhere; add a lint rule).
5. **Frontend**: Next.js (App Router) + TypeScript. Charts rebuilt from the same Vega-Lite specs as `charts.py`
   (serve the specs from the API so there is one source of truth).
6. **Hosting**: the frontend on a static/edge host, the API on a container host with ≥1 GB RAM. Write the
   monthly cost estimate into the log **before** deploying, and get the human's OK.

## Steps

1. Decision logged; if skipped, stop.
2. API + serialisation + tests (round-trip golden_us; a Decimal string survives; Unavailable shape; size limit).
3. Parity checklist file `docs/roadmap/T3.3-parity.md`, one line per Streamlit feature. Build page by page,
   ticking items.
4. Playwright end-to-end tests for: upload → results; click a value → highlighted source; Q&A refusal.
5. Deploy to preview; cost approved; then production. Streamlit keeps running until the checklist is 100%.

## Acceptance criteria

1. Every parity item is ticked, each with an e2e test or a manual note.
2. The numbers shown in both UIs are identical for the golden fixtures and 3 real reports (a script compares
   the API JSON rendered through `formatNumber` with `display.py` output).
3. Snapshot and dev eval unchanged (the analysis code is untouched).
4. A security checklist from design point 4 is verified item by item in the log.
