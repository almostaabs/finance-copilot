## Fix principle (applies to every bug)

- Turning a wrong value into a correct value is best.
- Turning it into an explicit `Unavailable` with a clear reason is acceptable.
- Any new wrong value anywhere fails the phase.
- No fuzzy matching, no magnitude-based guessing, no per-company special cases. Every fix is a general rule
  justified by evidence printed in the document itself.

## Steps (in this order; one sub-step and at least one commit per bug)

### 1. T1.1-a: footnote/VIE tables read as the main statement

JPM p169 (total assets / total liabilities from the VIE table under footnote (a)); F p116 (cash from the VIE
table under the balance sheet).

1. **Reproduce first** (`uv run python -m evals.run --split dev --only JPM`, same for `F`) and find the root
   cause before changing code: is it page stitching, candidate/table choice, or row mapping across two
   tables on the same page? Record the root cause in the commit message and the KNOWN_ISSUES entry.
2. Fix the cause, not the symptom.
3. Regression: a synthetic fixture with a main balance sheet plus a small VIE table below it on the same
   page, both containing a `Total assets` row. The balance sheet's total must win (or the concept must be
   withheld with a clear reason); the VIE total must never be mapped.

### 2. T1.1-d: a "% of sales" column read as dollar amounts

LOW p41. A numeric column whose header contains `%`, or whose cells are percentages, must be excluded from
the period columns, the same way the Notes column is excluded.

Regression: a fixture with a `% Sales` column next to each year column. Amounts must map correctly; the
percentage values must never appear as values.

### 3. T1.1-e: a component row taken as COGS when a total row exists

HON p59: "Cost of products sold" chosen over "Total cost of products and services sold". Fix in mapping via
literal aliases and/or the conflict rules in `mapping/validate.py`, so that the total wins or the concept is
withheld as a conflict. **The component must never win.**

Tests in `tests/test_mapping_synonyms.py` and the validate tests.

### 4. T1.1-g: one filing labelled with different years per statement (decision required first)

HD: the income and cash-flow statements are headed "Fiscal 2025 / 2024 / 2023"; the balance sheet is headed
by dates ("February 1, 2026 / February 2, 2025"). Year labels differ per statement, so ratios pair
mismatched years.

**Before writing any code for this bug**, the builder stops and reports to the orchestrator, who presents
the human with:

- **(A)** reconcile the periods from evidence printed in the document (e.g. text stating which date the
  fiscal year ends), or
- **(B)** detect the mismatch and mark the affected periods `Unavailable(AMBIGUOUS)` so nothing is mis-paired,

with a recommendation. Code for this bug starts only after the human answers. The chosen design is then
recorded in this file as a dated amendment.

## Amendments

### 2026-09-24: bug 2 (T1.1-d) clarification, from the scout pre-flight

At LOW the year line (`2026 2025 2024`) sits above a second header line (`Amount % Sales Amount % Sales …`),
and the % cells are bare decimals (`66.52`). "Header" in step 2 therefore means **every header line above
the first data row**, including such a sub-header line; it must not be parsed as a body row. A sub-column
whose printed sub-header contains `%` is excluded like the Notes column. A year label spanning several
sub-columns goes to the sub-column the printed sub-header identifies as the amount, never by nearest centre
alone. If the amount column for a year cannot be identified from printed headers, the statement's periods
are withheld. Bare decimals are not evidence of a percentage.

### 2026-09-24: bug 4 (T1.1-g) decision, by the human: A with B as fallback

- Reconcile only from an explicit binding in **one sentence** (or one table row) that names both a fiscal-year
  label and an end date, e.g. "fiscal 2025 … ended February 1, 2026" or "fiscal year ended February 1, 2026
  ('fiscal 2025')". HD prints this on rendered page 4: `fiscal 2025 | Fiscal year ended February 1, 2026`.
  No inferring across sentences, no date arithmetic (no "52/53 weeks" reasoning).
- The bound date must **exactly equal** a date printed in a balance-sheet column header; otherwise fall back to B.
- Two bindings in the document that disagree → B, with both quoted in the reason.
- B = the document's periods are `Unavailable(AMBIGUOUS)` with a reason naming the mixed headers.
- Only filings whose statements actually mix "Fiscal YYYY" headers and date headers are touched. Filings with
  consistent headers (LOW, NVDA, WMT, December filers, all synthetic fixtures) must be **byte-identical** in the
  snapshot, and the evaluator must prove it.
- The binding sentence and its page go into the provenance/reason of the relabelled periods (e.g. the
  `Period.label`, which is excluded from comparison), so the relabel is traceable. No `types.py` contract change.
- Required tests: HD-like (binding found → relabel); mixed headers with no binding → AMBIGUOUS; conflicting
  bindings → AMBIGUOUS; binding date matching no column → AMBIGUOUS; date-only filing untouched.

### 2026-09-24: bug 1 (T1.1-a) decision, by the human: split tables + literal anchor forms

The root cause is that a page with no usable ruled table is read as one word grid, so a footnote/VIE table
under a statement becomes part of it (plus two label defects: "(Note 9)" cut at "9)", "(a)" markers not
stripped). The fix splits a page's grid at a year-only header line that follows data rows. That split alone
turns UPS revenue 2024/2025 from withheld to wrong, because UPS's "STATEMENTS OF CONSOLIDATED INCOME" matches
no anchor and the scored fallback then picks an MD&A segment table (rendered page 40). Decision:

- Keep the split. Add literal heading forms "Statements of Consolidated <X>" (income/operations, balance
  sheets/financial position, cash flows) to the anchor patterns, consolidated scope, each with a test.
  No looser matching.
- Report Deere's (`0001104659-25-122321`) outcome explicitly. If any Deere record, or any other dev record,
  becomes wrong: stop and show the human. No fallback logic to compensate.
- Every changed real-report snapshot line is listed and justified in the log; synthetic fixture lines must
  not change (new fixture lines excepted).
- Add a KNOWN_ISSUE (MEDIUM): "When no anchor matches, the scored fallback can select a non-statement table on
  a nearby page (seen with UPS before the anchor fix)." Not fixed in this phase.
- If this cannot reach 0 new wrong values, fall back to the labels-only fix for this phase (the T1.1-a records
  become withheld conflicts) and report why.
