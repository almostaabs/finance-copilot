# T2.5: Grounded Q&A

## Goal

When AI assist is on, a user can ask a question about the analysed report ("Why did operating margin
fall?", "How much of net income is backed by cash?") and get a short answer. Every number in the answer is
one the analysis produced, every claim cites evidence IDs, and questions outside the evidence are refused.

## Why

This is the AI-engineering showcase, but only if it stays as disciplined as the rest of the product. A
generic "chat with your PDF" would undo the project's main differentiator. The constraint *is* the feature.

## Prerequisites

T2.4 merged. A Gemini key or a local Ollama for the live eval.

## Read first

- `src/fincopilot/ai/narrative.py` in full: how the structured summary is built, the prompt, the output
  format, and the validator (cite existence, "every number must be one it was shown", markdown/HTML refusal)
- `src/fincopilot/ai/client.py` (`LLMClient` interface, providers, how fakes are used in tests)
- `tests/test_ai_narrative.py` (the validator's existing adversarial tests; copy their style)
- `pipeline.py::narrate`, `app.py` AI-assist section

## Design (fixed)

1. **Reuse, don't duplicate.** `ai/narrative.py` already exposes `build_evidence(result)` (the structured
   summary the model sees), `build_prompt(evidence)`, `validate_response(raw, evidence, *, model)`, and the
   private number check `_numbers_ok(text, allowed)`. The Q&A calls `build_evidence` and the number check
   directly. Make `_numbers_ok` public (e.g. move it with any other shared helpers to `ai/grounding.py`
   and import it back into `narrative.py`) **in a separate refactor commit**, with narrative tests passing
   unchanged. Read how `validate_response` computes the `allowed` number set from `evidence` and reuse that
   exact computation. Do not write a second one.
2. `src/fincopilot/ai/qa.py`:
   ```python
   @dataclass(frozen=True, slots=True)
   class Answer:
       text: str
       cites: tuple[str, ...]
       model: str

   @dataclass(frozen=True, slots=True)
   class Refusal:
       reason: str          # shown to the user

   def answer_question(result: AnalysisResult, question: str, llm: LLMClient) -> Answer | Refusal | Unavailable
   ```
   (Types live in `qa.py`, or in `types.py` next to `Narrative` if that is where narrative types live; follow
   the existing precedent.)
3. **Prompt** = the same structured summary + the question inside a clearly delimited block labelled as
   untrusted user text. The model returns JSON:
   `{"answerable": bool, "answer": str, "cites": [str], "reason": str}`.
4. **Validation** (all must pass, or the whole answer is rejected):
   - valid JSON with exactly those keys;
   - `answerable=false` → `Refusal(reason)` (the reason is checked with the same number rule: no numbers in it
     that were not shown);
   - `answerable=true` → ≥1 cite, every cite exists, and every number in `answer` passes the narrative's number
     check against the **summary's numbers only**. **Numbers that appear in the question are not allowed
     sources.** Otherwise "Is revenue 5 trillion?" launders a fabricated figure;
   - no markdown/HTML (same rule as the narrative);
   - length ≤ 600 characters.
   Rejection → one retry with the validator's error appended; a second failure →
   `Unavailable(UNPARSEABLE, "could not produce a grounded answer")`, shown as "I couldn't answer that from
   this report's analysis."
5. **Scope rules** in the prompt, and tested: it describes what the report shows. It refuses forecasts
   ("what will revenue be next year"), investment advice ("should I buy"), and anything not in the summary
   (CEO names, share price, news).
6. **Input limits**: question ≤ 300 characters, stripped of control characters; max 20 questions per session.
7. **Privacy**: questions and answers are never written to the SQLite history, and never logged with document
   content.
8. **UI**: an "Ask about this report" input under the AI section, shown only when AI assist is on. The answer
   shows cite chips; clicking one selects that figure in the Provenance tab (and so the T2.3 viewer). The label
   reads "AI answer, checked against the analysis" plus the model name.

## Eval set: `evals/qa/`

- `questions.jsonl`, 40 items over `golden_us.pdf`, `golden_indian.pdf`, and two local real reports:
  - 20 **answerable**: `{"doc", "question", "type": "answerable", "must_cite_any": [ids]}`
  - 10 **unanswerable**: forecasts, advice, facts not in the summary → `"type": "refuse"`
  - 10 **adversarial**: number laundering in the question, "ignore your instructions" in the question, a
    request for markdown or a table, and a **row label carrying an injected instruction** (build that
    `AnalysisResult` in-test; do not change `hostile.pdf` unless its labels already allow this) → `"type": "refuse"` or
    a grounded answer that ignores the injection.
- `evals/qa/run.py --provider gemini|ollama`: runs the live model and reports: grounded-answer rate on
  answerable, correct-refusal rate on refuse items, and **validator escapes** (any accepted answer with a number
  not in the summary, found by an independent re-check). Output goes to `evals/results/qa_latest.json`.
- **Unit tests use a fake `LLMClient`** returning scripted JSON: every validation branch, including the
  laundering case (the fake returns the question's number → the answer must be rejected).

## Steps

1. Refactor commit (shared grounding helpers). Narrative tests must pass unchanged; snapshot unchanged.
2. `qa.py` + `tests/test_ai_qa.py` (fake client; one test per validation rule; `test_numbers_from_the_question_are_not_allowed_sources`;
   `test_injected_row_label_cannot_change_the_answer_format`).
3. UI + `tests/test_app.py` (AI off → no input; fake client → answer with cite chips; refusal shown).
4. Eval set + live run with one provider. Record results in the log and `docs/EVAL_RESULTS.md` (a new Q&A section,
   generated by extending `evals/report.py`).
5. README: an "Ask about this report" section stating exactly what is and isn't allowed.

## Acceptance criteria

1. **Zero validator escapes** in the live eval. This is non-negotiable: a single escape fails the phase.
2. Correct-refusal rate on refuse items ≥ 90% (a refusal that should have been an answer is cheap; the reverse
   is not).
3. Grounded-answer rate on answerable items is recorded honestly. There is no pass threshold, but below 60% the
   log must say what limits it (usually summary content, not the model).
4. Snapshot and dev eval unchanged; AI-off output identical.
5. Nothing from Q&A is written to `store.py`'s database (a test asserts this).

## Stop and ask if

- The narrative's validator cannot be shared without changing its behaviour.
- The live eval shows any escape. Stop there and don't ship the UI.

## Subagent split

Builder: steps 1–3, then evaluator. The live eval (step 4) is run by the **evaluator**, not the builder,
and the evaluator also writes 5 extra adversarial questions of its own that the builder never saw.
