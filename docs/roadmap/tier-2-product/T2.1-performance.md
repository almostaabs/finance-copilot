# T2.1: Performance on large reports

## Goal

Cut analysis time on large reports (Wipro, 481 pages, about 90 s; Berkshire, 152 pages, about 40 s) **without
changing a single output**, and without increasing peak memory beyond what the hosted container can take.

## Why

Every tier-2 feature is demoed live. A 90-second spinner loses the reviewer before the provenance appears.

## Prerequisites

Tier 1 exit gate passed.

## Read first

- `src/fincopilot/extract/pdf.py` in full, especially `_page_texts`, the tight-tolerance re-read, the
  candidate-page table loop, and the memory comments about `page.close()` (the app was OOM-killed before)
- `src/fincopilot/extract/anchors.py`: `candidate_table_pages`
- `docs/KNOWN_ISSUES.md` item #0
- `app.py`: how results are cached (search for `cache`)

## Scope

In: measurement tooling, a speed-up that keeps outputs identical, docs.
Out: **early stopping** ("stop scanning once a statement cluster is found"). KNOWN_ISSUES says it changes
the extraction contract and needs a design pass. Not in this phase.

## Rule of this phase

**Measure before optimising.** The optimisation is chosen from the profile, not assumed. The snapshot
(fixtures + local real reports) and the dev eval must be **byte-identical** before and after.

## Steps

1. **Benchmark tool** `scripts/bench.py <pdf>... [--repeat 3]`: runs `pipeline.analyze` per file, reporting
   median wall time and peak RSS (`resource.getrusage(RUSAGE_SELF)` plus `RUSAGE_CHILDREN` for workers).
   It prints a Markdown table.
2. **Baseline**: bench the local real reports (all present in `tests/fixtures/real/`) and two rendered 10-Ks from
   `evals/.cache/pdf/`. Record the results in the log.
3. **Profile**: `uv run python -m cProfile -o /tmp/wipro.prof scripts/bench.py <wipro> --repeat 1`, then
   print the top 20 by cumulative time. Record the split in the log: page-text pass vs table extraction on
   candidate pages vs everything else.
4. **Choose the option from the profile:**
   - **If the page-text pass dominates** (the expected case): parallelise `_page_texts` across page ranges with
     `concurrent.futures.ProcessPoolExecutor`. Each worker opens its own `pdfplumber.open(io.BytesIO(data))`,
     extracts its contiguous page range with the given `x_tolerance`, closes each page as the current code does,
     and returns a list of strings. The results are concatenated **in page order**. The tight-tolerance re-read
     uses the same parallel function. The worker count comes from the env var `FINCOPILOT_WORKERS`: default
     `min(4, os.cpu_count() or 1)`, and `1` means the exact current sequential code path (keep it as the
     fallback, not a copy). Do not parallelise for documents under 60 pages (the overhead wins); make 60 a named
     constant.
   - **If table extraction on candidate pages dominates**: stop and ask. Reducing candidate pages changes
     which tables are seen, so it is a design decision.
5. **Hosted memory**: each worker re-parses the PDF. Measure peak RSS with 1, 2 and 4 workers on Wipro.
   If 2 workers exceed 800 MB peak, the hosted default must be 1. Document the recommended
   `FINCOPILOT_WORKERS` for Streamlit Community Cloud in the README's hosted table.
6. Tests in `tests/test_extract_pdf.py`:
   - `test_parallel_page_text_equals_sequential`: on `golden_indian.pdf` and `stitched.pdf`, forced to 2 workers
     with the page threshold patched to 0, the texts are identical to the 1-worker output.
   - `test_workers_env_var_one_uses_sequential_path`.
7. Update README ("A 480-page report takes about 90 seconds" → the measured figure) and close or update
   KNOWN_ISSUES #0.

## Acceptance criteria

1. `scripts/snapshot.py --check` shows no diff, including `.snapshots/real.snap`.
2. Dev eval `--compare`: zero deltas in every count.
3. Bench table before/after in the log, with ≥30% median wall-time reduction on the largest report.
   **If the profile shows this is not achievable within scope, the honest result is "no change", with the
   profile as evidence.** That is an acceptable outcome; forcing it is not.
4. Peak RSS for the recommended hosted setting is recorded and below 800 MB on Wipro.
5. `FINCOPILOT_WORKERS=1` reproduces the old code path exactly (test 6b).

## Stop and ask if

- The profile says table extraction dominates.
- Parallel output differs from sequential on any real report.

## Subagent split

Builder: steps 1–3, then reports the profile to the orchestrator, which confirms the option before
steps 4–7. The evaluator re-runs the bench independently; numbers must be within 15% of the builder's.
